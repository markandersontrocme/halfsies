# Halfsies design

Halfsies is a macOS menu bar app for ZMK split keyboards.
This document records the decisions agreed on 2026-11-09.
The research behind them is in [research/](research/README.md).

## Audience

Built for the owner and for other ZMK split users.
The code and data model should not assume a single user.
A new user sees nothing in the menu bar until Bluetooth access, Bluetooth itself, and the firmware are right, so Settings explains what is missing.
There is no welcome window or setup wizard.

## v1 scope

- Show the battery level of both halves of one keyboard.
- Show whether each half is connected.
- Launch at login.
- The data model supports several keyboards and any number of parts; the UI shows one keyboard.

Deferred to later versions: low-battery alerts, showing several keyboards at once, dongle setups, layer display.

## Platform and tooling

- Swift 6 with strict concurrency, `@Observable`, SwiftUI for all views.
- The menu bar item is an AppKit `NSStatusItem` that opens a SwiftUI panel in a borderless window.
  SwiftUI's `MenuBarExtra` is not used because its documented behavior does not cover a colored, non-template label image, which the low-battery state needs.
- Current macOS only (26 and later).
- Unsandboxed, no Apple Developer Program, no notarization.
- Local builds are signed with a free Personal Team development certificate so the Bluetooth permission survives rebuilds.
- Public CoreBluetooth APIs only; the private IOKit power-source API is not used.
- A thin Xcode app target generated by XcodeGen, with nearly all code in a local Swift package.
- MIT license.

## Distribution

- Beta builds are GitHub prereleases with the app zipped by `ditto`.
  There is no DMG, Homebrew cask, or in-app updater.
- A release starts either from pushing a `v1.2.3` tag or from running the CI workflow by hand on `main` with tag `v1.2.3`, which creates the tag.
  Either way CI tests the package, builds the Release configuration, and publishes `Halfsies-1.2.3.zip`.
  The tag sets the marketing version, and the CI run number sets the build number.
- `scripts/package.sh` builds and zips the app.
  It builds from the committed files only, so a developer's gitignored `Config/Local.xcconfig` cannot change a release build.
  CI runs the same script on every pull request and keeps the zip as a workflow artifact.
- Release builds are ad-hoc signed with the hardened runtime and are not notarized.
  Every update is a new quarantined download, so users approve it in Gatekeeper again, and the new signature asks for Bluetooth access again.
  A stable self-signed certificate would only save the Bluetooth prompt, at the cost of a secret to store, back up, and rotate.
  Revisit if beta users complain about update friction.
- Release builds are Apple silicon only, because the Intel build is untested.

## Reading battery levels

- Attach to the keyboard connection macOS already holds and read every Battery Service (0x180F) instance.
- Identify each part from its descriptors, never from discovery order:
  - Presentation Format (0x2904) description `0x0106` ("main") is the central half.
  - Presentation Format description `0x0108` ("auxiliary") with User Description (0x2901) `Peripheral N` is peripheral N.
- Subscribe to Battery Level notifications and re-read every 60 seconds as a safety net.
- Look for newly connected keyboards every 10 seconds, because CoreBluetooth on macOS has no callback for that.
- The transport publishes Bluetooth availability alongside the keyboards, so the UI can explain an empty menu bar without importing CoreBluetooth.
  Until the first state update arrives, the app is waiting for the user to answer the permission prompt, not failing.
- If a read fails before a keyboard is fully read, drop it and let a later discovery pass attach again.
  Dropping ends only the app's own connection; macOS keeps the keyboard connected.
- A failed re-read keeps the last level.
  After 3 failed re-reads in a row, the keyboard is dropped the same way.
- A keyboard that keeps failing waits 10 seconds before the next attach, doubling after each failure up to 5 minutes.
- A level of 0% means the part is disconnected or asleep, and is shown as a dash, never as 0%.

## Presentation

- The menu bar shows the split ring, then two percentages, left then right, for example `86% 39%`, with no `L` or `R` labels.
- The split ring is the app's mark: a circle cut into a left and a right half, each filled from the bottom up with that half's battery.
  The same drawing is used in the menu bar, in the panel, and for the app icon.
- A half at 20% or less is red.
  Otherwise the item is a template image, so it follows the menu bar's text color.
- A disconnected part shows a dash in its place and a dotted half in the ring.
- A compact mode shows only the ring, without percentages.
- When no keyboard is connected, the menu bar item is hidden.
  Opening the app again (from Finder or Spotlight) opens Settings, so the app is never unreachable.
- Settings opens by itself on the first launch only.
  Later launches, including launch at login, stay quiet.
- Clicking the item opens a small panel (not a plain menu) with per-part detail, leaving room for future features such as the layer display.
- Settings live in a standard macOS Settings window opened from the panel.
  v1 settings: swap sides, launch at login, keyboard picker, compact menu bar.
- The top of Settings shows one setup status line, with an action where one exists:
  waiting for Bluetooth permission, permission denied (with a button to the Bluetooth privacy pane), Bluetooth off, Bluetooth unsupported, no keyboard connected, the picked keyboard not connected, a keyboard that reports only one battery (with firmware guidance), or the keyboard being shown.
- The bottom of Settings shows the app version and a link to the README troubleshooting section.

## Left and right

- The central half is left by default; a "swap sides" setting flips it.
- No first-run setup.

## Keyboard selection

- By default, pick the first connected keyboard that reports two or more Battery Service instances.
- The keyboard picker in Settings overrides the default.

## Firmware prerequisites

- The central half must be built with `CONFIG_ZMK_SPLIT_BLE_CENTRAL_BATTERY_LEVEL_FETCHING=y` and `CONFIG_ZMK_SPLIT_BLE_CENTRAL_BATTERY_LEVEL_PROXY=y`.
- The README documents this.
  When a keyboard reports only one battery, Settings names the two settings, mentions re-pairing, and links the README section.
- Future features may require adding community ZMK modules to the firmware, which is acceptable.

## Extensibility

- The core concept is a connected keyboard, with battery as one feature of it.
- Features are compile-time Swift modules registered in the app's composition root, not runtime plugins.
- The layer display is the confirmed next feature.
  Stock ZMK never sends layer state to the host, so it needs a firmware module on the central half.
  The leading option is a raw HID report on vendor usage page 0xFF60, read with `IOHIDManager`; see `research/04-layer-display.md`.

## Development workflow

- Write tests first for the core logic: parsing, identifying parts, and disconnected handling.
  Check the Bluetooth and UI layers by hand on real hardware.
- Swift Testing against fake transports; do not mock CoreBluetooth.
- Work on branches, merged into `main` through PRs.
- GitHub Actions builds and tests every PR.
- Before writing the app, a throwaway CoreBluetooth spike against a real keyboard checks the approach, and its findings go in `research/05-spike-results.md`.
